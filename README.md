# RS2 Branchline

**RailSim II 2.15 をベースとした、非公式の趣味フォーク**

> 開発名 **RS2EX** ／ 公開候補名 **RS2 Branchline**
> リポジトリ名は現在 `RS2EX` のままです。ソース中の `RS2EX...` という記号名や
> 改変表示（`// Modified for RS2EX on ...`）も、当面そのまま維持します。
> 開発の履歴は、見た目の統一よりも大切だと考えているためです。

---

## このプロジェクトについて

RS2 Branchline は、RailSim II に「自分が欲しかった機能」を加え、
現代的な環境でどこまで発展させられるかを試すための、
RailSim II 2.15 ベースの非公式な趣味フォークです。

本プロジェクトは公式な後継版や正統な発展版を名乗るものではなく、
RailSim II から分岐した**一つの別系統**として位置付けます。
また RailSim II k-build とも独立したプロジェクトであり、
置き換えや優劣を競うことを目的としていません。

コミュニティで広く利用されている拡張構文については、
既存資産を活用しやすくするため互換目的で解釈する場合があります。
ただし内部実装は RS2 Branchline 側で独自に行い、
k-build との完全互換を目標とはしません。

Public リポジトリでは、RailSim II 由来のコードと RS2 Branchline による変更、
設計判断、実装経緯を可能な限り追跡できる状態に保つことを重視します。

### 立ち位置を一文で

> **RS2 Branchline は RailSim II の次の本線ではなく、そこから分岐して伸びていくもう一本の線路である。**

## 系統

```
RailSim II 2.15
├─ k-build
└─ RS2 Branchline   ← このプロジェクト
```

これらは**別々の開発ブランチ**です。
同じ問題を違う方法で解くこともあります。

RS2 Branchline が新しい API や別のレンダラ、異なる機能を持っていたとしても、
それは k-build より「優れている」「正統である」ことの証拠にはなりません。

### この呼び方は使いません

公式な地位を示唆する表現は避けます。

> 公式後継 ／ 真の後継 ／ 次世代 RailSim II ／ 決定版 ／ 公式な継続 ／ k-build の置き換え ／ 上位版

### この呼び方をします

> 非公式の趣味フォーク ／ 独立した派生 ／ 別系統のブランチ ／ 実験的フォーク ／ 個人の開発ブランチ ／ RailSim II ベースのプロジェクト

**Branchline（支線）** という名前は、新しい本線ではなく
横に伸びる一本の線であることを示すために選んでいます。

## 開発の進めかた

### 置き換える前に、境界を作る

大きな subsystem を入れ替えるときは、いきなり書き換えず、
先に責務の境界を作ってから中身を差し替えます。

```
レガシー挙動を理解する
      ↓
責務を分離する
      ↓
互換性を保つ
      ↓
置き換えの境界を導入する
      ↓
実装を置き換える
```

複数の依存しあう系を同時に書き直すより、この順序を優先します。

### 古いコードは、まず証拠として読む

古く見えるコードや変わった書き方を、自動的に「間違い」とは見なしません。
RailSim II は今とはまったく違うハードウェアとソフトウェアの制約のもとで設計されています。

DirectX 8、DirectInput、DirectPlay、フレーム基準のタイミング、
GDI ベースのキャプチャ、無圧縮 AVI、Win32 前提 — これらは
当時のハードウェアに対する妥当な解だった可能性があります。

**置き換える前に、それが元々どんな問題を解いていたのかを突き止める。**
歴史的な制約を理解すると、現代的な置き換えの設計はむしろ簡単になります。

実際、この方針は結果につながっています。v0.0.6 でメッシュの所有権を分離したとき、
2002年のコードが「ピッキングとシャドウから読めるように」メッシュをシステムメモリに
置いていた理由が分かり、CPU と GPU の役割を分けた結果として
CPU 使用率が約 34% 下がりました。速くするための変更ではありませんでした。

### 既知の問題は、生き残ってよい

作業中に無関係な既存の不具合を見つけても、その場では直しません。

1. 可能なら再現する
2. 観察を記録する
3. 影響する subsystem を特定する
4. Known Issue として残す
5. 現在のバージョンの目的を妨げない限り、そのまま進む

これは、近代化作業が際限なく膨らむのを防ぐためです。

### AI 支援開発について

本プロジェクトは AI 支援による開発を積極的に利用しています。

AI を使うことは、変更が理解可能でレビュー可能であるべきという責任を変えません。
そのため次を重視します。

- 大きな変更の前に設計書を書く
- 目的の明確な小さいコミットに分ける
- スコープの境界を明示する
- 手動テストの結果を記録する
- 既知の問題を文書化する
- レガシーコードは保守的に変更する
- 意味が不明なときは推測せず質問する

AI エージェントは実装の共同作業者であって、
作者や由来を曖昧にしてよい理由ではありません。
**どのツールが書いたか知らなくても内容が理解できる**状態を目指します。

## 現在の状態

upstream は RailSim II 2.15（`Version 2.15 source code`）。
そこから **126 コミット**、17 バージョンぶんの作業を積んでいます。

| バージョン | 内容 |
|---|---|
| **v0.0.1** | Fixed Simulation Tick Foundation — シミュレーションを描画フレームから切り離し、30 Hz 固定に |
| **v0.0.2** | 60 FPS Render Loop Decoupling — 描画を 60 FPS へ。シミュレーション速度は不変 |
| **v0.0.3** | Train Render Interpolation — 列車の描画補間。30 Hz の動きを 60 FPS で滑らかに |
| **v0.0.4** | D3D8 Renderer Boundary — デバイスとフレームのライフサイクルに境界を作る |
| **v0.0.5** | GPU Resource Lifetime Boundary — GPU 資源の寿命と所有権に境界を作る |
| **v0.0.6** | Mesh Ownership Boundary — `ID3DXMesh` を実行時のメッシュ所有者から外す |
| **v0.0.7** | Material Data & Sampled Texture Binding Boundary — マテリアルとテクスチャを RailSim 自身のデータにする |
| **v0.0.8** | Render-State Boundary — 描画状態を「API の値」ではなく「意味」で要求する形に |
| **v0.0.9** | Draw Boundary and DX12 Readiness — 描画そのものをゲームコードから外す |
| **v0.1.0** | Direct3D 12 Backend Bootstrap — D3D12 で device と swap chain とフレームを所有し、クリアして present する |
| **v0.1.1** | First D3D12 Visible Draw Pipeline — RailSim のジオメトリが D3D12 のパイプラインを通って画面に出る |
| **v0.1.2** | Base Texture Sampling — D3D12 の実シーンで Stage 0 の PNG/BMP・埋め込み BMP テクスチャを表示する。標準レール・枕木の行列初期化漏れも修正 |
| **v0.1.3** | Material & Lighting Fidelity + DDS Base Texture — D3D12 にマテリアルと固定機能互換の照明、DDS（BC1/BC3）のベース色テクスチャを加える |
| **v0.1.4** | Stage 1 / Environment Mapping / UV Transform — D3D12 に 2 枚目のテクスチャ、環境マップ（窓や車体の映り込み）、UV 変換を加える |
| **v0.1.5** | Stencil Shadow Compatibility — 既存のステンシル影（Ctrl+S）を D3D12 で実行する。2D 画面座標の 0.5 画素のずれも修正 |
| **v0.1.6** | Mutable Texture / Text Compatibility — 可変テクスチャを D3D12 に加え、上部バー・ボタン・ダイアログの文字と入力欄の入力中の文字を D3D12 で表示する |
| **v0.2.0** | Legacy Independence & Native Widescreen — Direct3D 8 / D3DX8 をビルドと実行の要件から外し（`.x` は自前の importer で取り込む）、描画の大きさを実際のウィンドウに合わせて 16:9 を引き伸ばさずに表示する。保存ファイルに RS2EX の識別を入れる（手動確認待ち） |

### 到達した構造

```
30 Hz 権威シミュレーション → 描画補間レイヤ → 60 FPS 提示

.x ファイル → RS2 の text .x importer（D3DX8 の出力を実測して合わせたもの）
                    ↓
          RS2 が所有する CPU ジオメトリ
            ├→ ピッキング／シャドウ／境界計算
            ↓
          RS2 が所有するマテリアル／テクスチャ／描画状態
                    ↓
     描画境界（何を描くかだけを渡す。API の語彙は出てこない）
                    ↓
            Direct3D 12 バックエンド
     （back buffer = 実際のウィンドウ／モニターの大きさ）

保存ファイル → RS2EX の識別（製品・schema）で分類 → 旧形式は確認してから
```

タイミング、デバイス寿命、資源寿命、メッシュ所有権、
マテリアル、描画状態、描画そのものが、
それぞれ**一箇所に集まった**状態です。

v0.1.6 の時点で、**同じシーンが Direct3D 12 でマテリアルの色と陰影を持って描画され、
車両プラグインの DDS テクスチャも表示され、窓や車体には環境マップの映り込みが載り、
ステンシル影（Ctrl+S）も落ち、上部バーやダイアログの文字も出ます**。
影は RailSim II の影の処理そのものを Direct3D 12 で実行しており、
影が落ちる範囲は Direct3D 8 とほぼ同じです（実シーンで影の範囲の重なり 93%、濃さは同じ）。
照明は Direct3D 8 の固定機能と同じ式を頂点ごとに再現しており、
2 枚目のテクスチャの合成、環境マップの座標生成、UV 変換も、
Direct3D 8 で実測した挙動をそのまま再現しています
（確認用の図では、filter の境目のわずかな丸めの差を除いて Direct3D 8 と一致します）。
文字は RailSim II の文字の作り方（GDI で描いて 16 bit のテクスチャに書き込む）をそのまま使い、
Direct3D 12 がその書き換えを Direct3D 8 と同じ意味で扱います（確認用の図と実シーンの上部バーで Direct3D 8 と画素単位で一致）。
検証に使った場面では、影 ON を含めて、
Direct3D 12 がまだ扱えない描画の呼び出しは 0 種になりました。
PBR（物理ベースレンダリング）には手を付けていません。
DDS はあくまでテクスチャの入れ物として扱い、法線マップなどの意味付けはしていません。

v0.2.0 で **Direct3D 12 が唯一のレンダラ**になりました。

> **RS2EX no longer requires Direct3D 8 / D3DX8 for its supported D3D12 runtime and accepted legacy `.x` content path.**

Direct3D 8 のバックエンド、`.x` の取り込みのためだけに作っていた Direct3D 8 の device、
D3DX8 の数学関数は取り除き、DirectX 8.1 SDK なしでビルドできます。
`.x` は RailSim II の実際のコンテンツ 264 ファイルについて、D3DX8 が返していた
形・材質・法線・bounds を実測し、同じ結果を返す自前の importer に置き換えました
（面の順だけはファイルの順のまま）。
DirectInput・DirectSound などは残っており、古い DirectX の部品をすべて外したわけではありません。

画面の大きさは設定の解像度に固定せず、実際の back buffer の大きさに合わせます。
16:9 のウィンドウや枠なし全画面（モニターの解像度）では横に広く見え、
上部バーや右パネルは実際の端に付き、文字や部品は引き伸ばされません。
設定画面に 16:9 の解像度を加えました。大きさは起動時に決まります。

保存ファイルの先頭に RS2EX の識別（製品と保存形式の版）を入れ、
RailSim II や v0.1.x までの形式のファイルは、互換を保証しない旨を示して確認してから開きます。
新しすぎる形式や壊れたファイルは開きません。

ネットワーク機能（DirectPlay のセッション）は v0.2.0 で外しました。
スクリーンショット・動画の撮影は、Direct3D 12 に画面の読み戻しがまだないため使えません。

v0.2.0 の自動検証は合格し、実機での手動確認を待っています。
v0.1.6 の手動確認（ウィンドウ・枠なし全画面）は合格しています。

**自動フォールバックはしません。** Direct3D 12 が使えない環境では、
理由を示して起動をやめます。

境界を先に作るやりかたの結果として、Direct3D 12 バックエンドの追加で
ゲーム側に入った変更は、起動スイッチを読む 1 箇所だけです。
**描画を行うゲームコードは 1 行も変わっていません。**

### 機能を選ぶ基準

次のいずれかを満たすとき、その機能はこのプロジェクトに入ります。

- 開発者本人が欲しい
- 後の作業のための技術的な土台が良くなる
- 既存の RailSim II 資産を現代の環境に持ち越せる
- 元の構造では難しかった実験ができるようになる
- 既存コンテンツを不必要に壊さずに、使い心地が良くなる

**他の派生に同じ機能があることは、実装する理由にも避ける理由にもなりません。**

## 互換性の方針

> **有用なところでは互換性を保つ。ただし互換性のために、このプロジェクトが
> 目指したものになれないのなら、それは本末転倒である。**

タイミング、描画ループ、グラフィックス API、マテリアル系、動画キャプチャ、
列車の挙動、音声、プラグインメタデータ、シミュレーション機能などは
近代化・置き換えの対象になり得ます。
そのうえで、既存の RailSim II コンテンツが動き続けるよう努めます。

衝突したときの優先順位は、おおよそ次のとおりです。

1. プロジェクトの構造的な一貫性
2. 既存の RailSim II 2.15 コンテンツとの互換性
3. よく使われる拡張構文の穏当な処理
4. 特定の k-build 拡張との任意互換
5. 他フォークとの厳密な挙動一致

### k-build 拡張構文について

方針は **「有用なら互換構文を、実装は独自に」** です。

1. 挙動を再現するためだけに実装コードを写さない
2. 既存の拡張構文を採用するときは、その出自を記録する
3. ライセンスと方針が明示的に許す場合を除き、機能は独自に実装する
4. 実際に試して意図的に対応していない限り、k-build 完全互換を称さない
5. 未知・未対応の拡張データは、できる限り穏当に処理する
6. 可能な範囲で RailSim II 標準の挙動を基準の fallback とする

## このリポジトリの読み方

公開している目的のひとつは、変更と開発の経緯を追跡可能にしておくことです。
Git 履歴から次が分かるようにしています。

- RailSim II から継承したもの
- 変更したもの
- いつ変更したか
- なぜ変更したか
- upstream と意図的に挙動が異なる箇所
- 他のエコシステムから採用した互換構文
- RS2 Branchline 独自の実装

各バージョンには注釈付きタグが付いており、
そのバージョンで何を変え、何を**意図的に変えなかったか**、
どう検証したかをタグメッセージに記録しています。

```
git tag -l -n50 v0.1.0
```
